## FOUNDER DECISION 1 — BIDIRECTIONAL MATCHING

V001 Matching must support BOTH directions:

### Direction A

Requirement → Matching Properties

The broker can start from a Buyer/Tenant Requirement and identify matching Properties from the broker's own inventory.

### Direction B

Property → Matching Requirements / Relevant Clients

The broker can start from a Property and identify matching Buyer/Tenant Requirements associated with relevant contacts in the broker's own data.

Both directions must follow the same frozen product principle:

**Compare → Score → Explain**

Matching remains:

- broker-initiated
- rule-based
- per-broker
- private
- non-AI
- non-marketplace

Do NOT define:

- scoring weights
- scoring thresholds beyond already frozen governance
- algorithms
- queries
- schema
- automatic alerts
- push notifications
- ML
- embeddings
- cross-broker matching

This decision establishes only the PRODUCT BEHAVIOR boundary:

**Matching in V001 is bidirectional.**

## FOUNDER DECISION 2 — MULTIPLE REQUIREMENTS PER BUYER / TENANT

A Buyer or Tenant contact may have:

**one or more Requirements**

This supports real broker cases where the same client may have different simultaneous property needs.

Examples are NOT to be converted into implementation rules.

Do NOT define:

- active/inactive requirement status
- maximum number of requirements
- requirement priority
- requirement version history
- requirement expiration
- database cardinality implementation
- schema relationships
- UI tabs
- requirement grouping

The product-level minimum is only:

> A Buyer/Tenant contact can have multiple distinct Requirements, and each Requirement can independently participate in Matching.

Capture First → Enrich Later must remain preserved.
